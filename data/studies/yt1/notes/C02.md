# C02 - 8-55 EMA pullback on NQ (long only)

Module: `tools/yt1/s_C02.py`. Variants: `base` 5-minute, `nb1` 3-minute, `nb2` 15-minute bars (`bar` parameter).

## 1. Readings added beyond the spec text
- **Signal window on the neighbours.** "Signal bars opening 10:00 ... 15:50" is applied literally to every bar size:
  3-minute bars opening 10:00 ... 15:48, 15-minute bars opening 10:00 ... 15:45 (the 15:45 bar closes on the flat bar
  and is therefore never traded).
- **"A low was below EMA55 within the last 6 bars"** = some bar among k-5 ... k (signal bar included) had its low below
  its own EMA55 (the script's `barssince(...) < 6`).
- **Trailing stop, "since entry".** The entry is at the signal bar's close, so the signal bar's own high is not in the
  trail. The first level is 0.9925 x the high of the next N-minute bar, known at that bar's close and working from
  the following minute. Until then the trade has no stop at all (the spec says "no initial stop").
- **The trail moves at N-minute bar closes**, not every minute ("bar high" = the high of a completed bar of the rule's
  timeframe). Between closes the last level is carried forward.
- **Trail level rounded to the nearest tick** (`core.tick_round`); the spec does not say how a percentage level lands
  on the tick grid.
- **"A bar that turns bearish"** = the first N-minute bar after the entry on which EMA55 <= EMA165 and EMA8 < EMA55,
  exit at that bar's close (a state test on each bar, as the script does; the entry bar is bullish by construction).
- **R unit** = 0.1 x `days.atr` (daily ATR(14) through the previous trading day), per the common rules.
- Every bar that meets the entry conditions is a candidate order; `run_orders` takes the first one while flat, so
  re-entries the same day are allowed (frame: any number a day).
- Not in the spec text, not coded: the script's "yesterday's volume >= 1000" filter (always true on MNQ).

## 2. Coding errors found after first seeing results
None. The module was not changed after the first run.

Representation note (not a change of rule): a per-order `trail` array of full length would need about 10 MB per order
x 4,283 candidate orders, so each order carries a small array-like (`_Trail`: the day's slice and its offset, NaN
elsewhere) that answers `trail[j]` and `np.asarray(trail)` exactly as the dense array would. Checked: element by
element equal to the dense array; and a deliberately leaky trail (each minute also seeing the level five minutes
ahead) makes `core.causal_check` FAIL, so the look-ahead test does read inside it.

`--check` prints "the sampled order is not reproduced on the 150-day window" on every sample: the order is there, but
`r_pts` = 0.1 x daily ATR differs in the 3rd decimal (28.8898 vs 28.8864 in the case examined) because the Wilder ATR
is seeded at the start of the 150-day window. The trail slice of that order is identical in both.
